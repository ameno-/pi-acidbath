# ADR-0002: Explicit model roles with visible fallback

## Status
Accepted

*Tracked in Beads:* [acidbath-9ih.2](bd-acidbath-9ih.2)
*Linear:* [MIGHT-496](https://linear.app/acids/issue/MIGHT-496/acidbath-harness-explicit-model-roles-and-fallback-routing)
*Date:* 2026-09-23
*Author:* Ameno

## Context
OMP uses role aliases (`default`, `smol`, `slow`, `vision`, `plan`, `commit`, `task`, `advisor`, `tiny`) plus fallback chains. Pi already has presets, `setModel`, `setThinkingLevel`, and `setActiveTools`. Silent permission or tool changes would violate Acidbath's capability-before-launch rule.

## Decision
Roles are user-selected via `/role`. Registry lives in `config/roles.example.json`, overridable by `PI_ACIDBATH_ROLES_PATH`. Resolution prefers scoped models, then exact registry hits, then an ordered fallback list. Every outcome notifies. Tools change only when a role defines a non-empty `tools` list. Clearing a role restores the pre-role model, thinking, and tools snapshot.

## Alternatives Considered
- Automatic intent routing: rejected; that is OMP policy, out of scope.
- Hard-coded aliases in source: rejected; users must add/remove roles without editing the extension.

## Consequences
* Predictable, restorable routing.
* Fallback can still change the live model, but never silently.
* Handoff, recap, compaction, and subagent profiles consume named roles rather than inventing their own model pickers.

## Amendment 2026-10-02 — selection interface and capability

Post-merge review found the selection UX missed what makes OMP's roles
usable: they are assigned through an interactive picker over a rich model
catalog and cycled with one action, not typed from memory. Amendment
(same registry, same resolution semantics, glue in
`extensions/harness/index.ts`):

* `/role set` with no argument opens a Pi `ui.select` picker of roles
  (label includes description, model name, thinking). Dialog-less modes
  (print/json) keep requiring a typed selector; `hasUI` is the guard.
* `/role models [query]` renders the live catalog with Pi's model
  metadata: human name, context window, USD per Mtok, reasoning, vision —
  matching `pi models` conventions. Unknown queries get "did you mean"
  suggestions.
* `/role next` cycles a persisted `cycle` list (default
  `smol → default → slow`, OMP `cycleOrder` parity). Fallback resolutions
  do not count as cycle hits: cycling is deliberate, entries whose model
  is unavailable are skipped and reported.
* Direct `provider/model[:thinking]` selectors bypass the registry for
  one-off switches and are persisted/restored like alias selectors.
* `/role add` gains a guided flow (alias → filter → model picker →
  thinking level limited by the model's `thinkingLevelMap` → description
  → optional immediate switch).
* Registry aliases keep descriptions and thinking levels visible in
  `/role list` and a new `/role info <alias>`.

Not adopted from OMP (still deliberate non-goals): automatic intent
routing, runtime retry/fallback chains, model-kind roles (image/web/tts),
and project-scoped role storage.

## Amendment 2026-10-07 — provider-exposed model refs

The shipped registry pinned `anthropic/claude-opus-4-1`-style pairs, which
resolved against providers the user may not have (here: every default role
was dead). Roles can now reference models the way **the provider's catalog
exposes them** (`modelRef: "Opus"`), and the reference is re-bound against
the live catalog at each resolution:

* `RoleSpec` gains `modelRef`; exactly one of `ref`, `provider+model`,
  or `modelRef` per alias (parser rejects mixtures with clear
  `RangeError`s — a partial `provider` with a `ref` is also rejected).
* Pure `matchModelRef(query, catalog)` mirrors Pi's own search tiers
  (id exact → id prefix → name exact/prefix → id substring → name
  substring). Equal-best hits fail **closed** with an
  `ambiguous-model-ref` error listing candidates — a role named "Opus"
  must never silently land on whichever model sorts first.
* A ref that no longer matches (catalog renamed, provider removed) is
  `unresolvable-model-ref`. That failure prefers the registry's fallback
  chain like any other unavailable spec; when no fallback satisfies, the
  error reports the bind reason (not a generic "unavailable") so the user
  sees why the role died.
* Provider is deliberately excluded from matching, so `"Opus"` survives
  the model migrating across providers (`ap-codex/...` → `future-lab/...`).
* Glue (`/role list`, `/role info`, picker labels, all `/role set|next|
  resolve` paths, agents profile resolution, and the compaction "compact"
  role) passes named `ModelInfo`s, not bare `{provider,id}` pairs.
  Unbound refs display as `~ "<ref>" (resolved from catalog at use)`.
* `/role add` accepts `<provider/model>` (pinned) or a catalog name
  (single word, e.g. `gpt-5.6-sol`; ambiguity is rejected at add time
  with the candidate list). `config/roles.example.json` and
  `defaultRoleRegistry()` now ship modelRef roles plus one `pinned`
  example role showing the provider/model escape hatch.
